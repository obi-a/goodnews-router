# Send UDP and HTTP traffic through the router

Use these exercises after the [main lab setup](stage1.md). They work in both
Fish and Bash. Start from `lab/stage1.json`, with checksum verification and TTL
decrement enabled. Keep the namespaces and router running between exercises.

## Interfaces and application ports

`left` and `right` are the router's logical network interfaces. Each can receive
and transmit packets. They are named in `lab/stage1.json`:

| Router interface | Attachment in this lab | Router address |
| --- | --- | --- |
| `left` | TUN `gn0` in namespace `gn-h1` | `10.0.0.1/24` |
| `right` | TUN `gn0` in namespace `gn-h2` | `10.0.1.1/24` |

For h1 → h2 traffic, `left` is the incoming interface and `right` is the outgoing
interface. For the reply, those roles reverse. The software router uses open
TUN file descriptors as these attachments; it needs no physical Ethernet ports
for this stage. The `.1` router addresses live in Go's configuration.

UDP/TCP **port numbers**, such as 33434 and 8080, identify application endpoints
within a host. They are separate from the router's network interfaces.

## 1. Send a UDP packet to a closed port

Leave Terminal D without a server running on UDP port 33434. In Terminal C:

```sh
sudo ip netns exec gn-h1 ./bin/goodnews craft --interface gn0 --protocol udp
```

The command's parts mean:

| Part | What it does |
| --- | --- |
| `sudo` | Supplies the privileges for namespace access and raw packet sending |
| `ip netns exec gn-h1` | Runs the program in h1's network namespace |
| `./bin/goodnews craft` | Constructs and sends one packet, then exits |
| `--interface gn0` | Sends through h1's TUN device, which the router reads as `left` |
| `--protocol udp` | Places a UDP header and payload inside the IPv4 packet |

Its defaults are:

| Field | Value |
| --- | --- |
| Source IP / UDP port | `10.0.0.2:40000` |
| Destination IP / UDP port | `10.0.1.2:33434` |
| IPv4 TTL | 64 |
| Application payload | 32 generated bytes |
| Total IPv4 packet length | 60 bytes: 20 IP + 8 UDP + 32 payload |

You can make the addresses explicit with `--src 10.0.0.2 --dst 10.0.1.2`.
The current crafting command has fixed UDP ports and supports ICMP or UDP.
These address defaults are packet fields, not values discovered from the
selected interface. When crafting from h2, set `--src 10.0.1.2 --dst 10.0.0.2`
explicitly to reverse the direction.

`craft` builds the IP header, UDP header and payload itself. It sends them using
an AF_PACKET socket on `gn0`, which preserves the deliberately malformed bytes
used in other experiments. It does not open a receiving UDP socket on port
40000, wait for an application reply, or print replies. Silence after a
successful command is expected; inspect the dashboard or capture for the result.

With h2's UDP port closed and ICMP responses allowed, expect:

1. UDP forwarded from `left` to `right`, with TTL reduced by one.
2. An ICMP Destination Unreachable, type 3/code 3 (**Port Unreachable**), from
   h2 (`10.0.1.2`), forwarded back from `right` to `left`.

Both records normally have router action `forward`. The host rejected the
application port; the router successfully carried the packets. This does not
mean UDP itself is unreachable or unsupported.

## 2. Run a UDP echo server and receive a reply

In Terminal D, start an application listening on h2's UDP port 33434:

```sh
sudo ip netns exec gn-h2 python3 -u -c '
import socket

with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as server:
    server.bind(("10.0.1.2", 33434))
    print("UDP echo server listening on 10.0.1.2:33434", flush=True)
    while True:
        data, peer = server.recvfrom(4096)
        print("Received", repr(data), "from", peer, flush=True)
        server.sendto(b"echo: " + data, peer)
'
```

The server waits for a datagram and sends its contents back with an `echo:`
prefix. Leave it running.

In Terminal C, use an actual UDP socket so an application is listening for the
reply at h1's source port:

```sh
sudo ip netns exec gn-h1 python3 -c '
import socket

with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as client:
    client.bind(("10.0.0.2", 40000))
    client.settimeout(3)
    client.sendto(b"hello from h1", ("10.0.1.2", 33434))
    data, peer = client.recvfrom(4096)
    print("Reply from", peer, ":", data.decode())
'
```

Expect Terminal D to show the received message and Terminal C to print a reply
containing `echo: hello from h1`. The dashboard should show two UDP forwards,
one in each direction.

This client uses normal UDP sockets: Linux constructs the UDP/IP headers. It
keeps its socket open to receive the response. In contrast, `craft` only sends
a raw packet. If you use `craft` against this echo server, h2 may reply after
`craft` exits, but h1 has no receiving socket on port 40000 and may return its
own ICMP Port Unreachable. Use the socket client for a complete exchange.

If needed, verify the server is listening:

```sh
sudo ip netns exec gn-h2 ss -lun
```

Look for `10.0.1.2:33434`. Stop the UDP server with Ctrl-C in Terminal D before
the next exercise.

## 3. Send an HTTP request over TCP

In Terminal D, start a web server bound to h2's address:

```sh
sudo ip netns exec gn-h2 python3 -m http.server 8080 --bind 10.0.1.2 --directory .
```

Because Terminal D is in the project directory, the server can return the
repository's `LICENSE` file. Leave it running. In Terminal C:

```sh
sudo ip netns exec gn-h1 curl -v --noproxy '*' --connect-timeout 2 --max-time 5 http://10.0.1.2:8080/LICENSE
```

`--noproxy '*'` makes curl connect directly to the lab host instead of using
any configured HTTP proxy. The timeouts bound how long a failed test can wait.
Expect HTTP status `200` and the license text, plus a request log in Terminal D.

The router forwards TCP/IP packets. The hosts establish the TCP connection,
exchange the HTTP request and response, and close the connection. Expect several
TCP records in both directions, rather than exactly one request packet and one
reply packet. The dashboard labels these TCP; it does not currently decode TCP
flags or HTTP contents.

To inspect TCP flags while repeating the request, run this in a spare terminal:

```sh
sudo ip netns exec gn-h1 tcpdump -nn -i gn0 'tcp port 8080'
```

You should see connection setup, data, acknowledgments and connection teardown.
Stop tcpdump with Ctrl-C when finished.

### Compare a missing resource and a missing server

With the HTTP server still running, request a nonexistent path:

```sh
sudo ip netns exec gn-h1 curl -i --noproxy '*' --connect-timeout 2 --max-time 5 http://10.0.1.2:8080/this-file-does-not-exist
```

Expect HTTP `404`. That is an application response: routing and the TCP
connection succeeded. A 404 is not a router drop.

Now stop the HTTP server with Ctrl-C in Terminal D and repeat the LICENSE
request. In the normal lab, h2 should reject the closed TCP port with a TCP
reset, and curl should report connection refused. The router can still show
successful forwarding in both directions.

## 4. Compare application failure with a missing route

In Terminal C:

```sh
sudo ip netns exec gn-h1 ./bin/goodnews craft --interface gn0 --protocol udp --dst 192.0.2.1
```

The base config has no route for `192.0.2.1`. Expect a `no_route` decision and a
generated ICMP type 3/code 0 (**Network Unreachable**) from the router's
`10.0.0.1` address. Compare this with Port Unreachable from h2 in exercise 1.

| Observation | Meaning in this lab |
| --- | --- |
| `forward` with an application reply | The router carried traffic and the application answered |
| ICMP Port Unreachable from h2 | The host was reached, but no UDP application accepted that port |
| TCP reset / connection refused | The host was reached, but the TCP connection was rejected |
| HTTP 404 | The web server answered, but the requested resource was missing |
| Router `no_route` and Network Unreachable | The forwarding table had no matching destination prefix |
| Client timeout | No expected reply arrived before the deadline; use traces/counters to locate the cause |

A timeout alone does not identify where traffic stopped. A stopped router,
packet filtering, a router drop, or an application that stays silent can all
produce one. UDP applications are not required to reply to every datagram.

When finished, stop any h2 server, quit the dashboard, stop the router, and run
`make lab-down`. Stop all namespace processes before cleanup.
